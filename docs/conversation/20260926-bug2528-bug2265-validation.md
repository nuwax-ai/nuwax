# #2528 / #2265 当前分支验收与剩余补修

## 基线与结论

- 基线 `7a9aa308118128096ecf8c36464d1f3f781fb89e` 已包含 `2234c7129` 的异常 close 终态补偿与 `4f7d62264` 的每连接静默 watchdog。
- 这次保留已有补修，新增的是 **sub 恢复后停止会话** 的遗漏：实际 HTTP SSE 验收中，后端已 `CANCEL`，页面仍 `active=true`，详情轮询停在 9。
- 原因：`runtime.stop()` 只 abort live，正在接管的 sub 没有被关闭；停止接口成功也没有写回绑定层的 `CANCEL`，页面仍被旧 `EXECUTING` 快照撑住。
- 修复：stop 同时关闭 live/sub，释放本轮终态等待；停止 API 业务成功后经统一终态入口写 `CANCEL`。失败响应 reject，旧停止请求迟到由会话和轮次归属拦住。

## 浏览器与实际 HTTP SSE

使用共享 Ego TaskSpace 22 的 p2、本分支 Umi dev `localhost:3000`。Mock 供数层与生产 `UnifiedChatSession`、runtime、SSE utility、恢复 Hook 共用真实 HTTP 连接。

- `NORMAL_SINGLE`、`IDLE_POLL_TERMINAL`、`NETWORK_ERROR`、`SUB_NETWORK_ERROR`、`SESSION_RESUME`、`LATE_CHUNK`：均实际开流后收口；无 FINAL 的 COMPLETE/FAILED 路径通过。
- 新增仅开发用 `POST /api/mock/conversation/disconnect/:id`：`mode=close` 不发 ERROR/FINAL 后直接结束 HTTP 流；详情分别置 `FAILED / COMPLETE / CANCEL`，三次都恢复 `active=false`。
- `mode=error` 保持服务端 EXECUTING，连续断流三次：事件累计 **9 → 18 → 27 → 36**，详情 poll **1 → 3 → 6 → 9**，各轮恢复为 1 条活跃 sub；耗时 **30.757s / 5.723s / 5.739s**。
- 修前 sub-stop：`server=CANCEL / active=true`。修后同路径：**`server=CANCEL / active=false / activeStreamCount=0`**，发送等待释放。
- 既有直接 SSE 测试覆盖重叠流独立 60 秒超时、待响应新连接、迟到 onopen、abort/close 交叠及三次重新连接；本次定向已执行。浏览器长期静默流也观察到 60 秒 watchdog 后恢复详情和 sub。

匿名页面的 `USER_CANCEL` / `MESSAGE_QUEUE_HOLDING` 本来预期悬挂，因此故障注入把它们置终态后，“悬挂场景保持活跃”默认断言会显示 false。本次按真实任务状态、active、HTTP 连接和消息恢复判断，不把这个场景默认断言当产品错误。

CDP 短时离线不会立即结束已建立 SSE；其证据不能替代主动 HTTP 断流。另有一次 Umi HMR 整页重载清除观测变量的中间尝试已排除。**没有宣称完成真实机器连续断网三次或原报告账户的现场复验。**
